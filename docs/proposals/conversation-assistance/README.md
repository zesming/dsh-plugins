## 方案定位

文中“已核实”表示固定基线源码或官方文档能够支持；“建议”表示本方案推荐的产品或技术选择；“待验证”表示开发前仍需实验或补充接口。产品参考能够证明交互方式，不能证明它们的内部提示词、模型路由或成本策略适合 DSH。[评审结论](conclusion.md)按基线实现复核了能力边界，与这三份方案冲突时以结论为准。

| 功能 | 归属 | 主要原因与实施前置 |
|---|---|---|
| 项目草稿 | DSH 仓库 PR | 搬运在 `ui-conversation` 内部，没有非替换式插件入口；附件运行时归属必须与导航语义一起改 |
| 提示词预测 | 本仓库插件 | 建议行、Tab / → 观测与安全插入都有公共入口；行内 ghost text 与辅助请求日志仍需上游 |
| 轮次 recap | 本仓库插件 | `facts` 可由客户端 Definition 完成；`semantic` 由 Host 生成，并与预测共享日志与计费缺口 |

这里区分功能的合理归属，不在本次 PR 修改上游或创建上游 PR。未来在本仓库实现插件时，遵循 [CONTRIBUTING.md](../../../CONTRIBUTING.md)：不替换已发布组件，不抢占其他包的单占位 slot，使用宿主 UI primitives、可释放的注册和双语文案。

## 共用约束

- 项目、Session 和轮次不能混用：草稿属于现有 Session；workspace 决定导航；预测和 recap 必须绑定生成它们的历史版本。
- 两类辅助推理都可关闭、可取消、有超时及预算上限，不调用工具、不唤醒主 agent，不使用 `followup` / `inject` 伪装用户输入。可抽取轻量共享模块处理生命周期、取消、预算和并发；内容、UI 与缓存键独立，不为了少一次请求而强行绑定预测和 recap。
- 默认只处理已经发送的当前会话内容，不额外检索 memory、apps 或其他项目，也不默认上传未发送草稿。
- 凡进入模型请求的内容都必须遵守 DSH 的可追溯日志规则。`ctx.llm.prepareCall` / `stream` 只是推理原语，不能替代日志设计；外部插件不能使用受限的 `appendPluginRecord` 绕过它。本轮已定：按“日志 + 代码内固定模板可重建 + 插件自有审计日志”处理，并在 README 与设置页说明这部分不计入 DSH 用量；完整记录能力列为后续上游事项。
- 灰色是视觉层级，不代表低对比度：支持深浅主题、缩放、键盘和读屏；预测不能进入实际编辑文档，recap 不能混入主 agent 正文或后续模型历史。

## 建议开发顺序

1. 上游 PR 先做“不覆盖目标草稿”（可单独合并），再做附件运行时归属，最后把选择器改为纯导航；D-06 是合并门槛。
2. 本仓库先交付 recap 的 `facts` 模式（不依赖模型），再交付预测（Host 候选 + 建议行 + Tab / → 与点击接受 + 总开关）。
3. 最后做 recap 的 `semantic`，按已定的宽松解读记录辅助请求，并在 README 写明它不计入 DSH 用量页。

三个方向已定：辅助请求按宽松解读记录、上游导航选纯导航并保留附件、接受键用 Tab / →。后续上游事项是辅助请求的完整记录能力与 composer suggestion（行内 hint）；其余实现前置与未验证项保留在对应文档中。
