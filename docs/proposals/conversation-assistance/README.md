# 对话输入与回顾方案

这组文档供开发前评审：整理按项目保留输入草稿、完成后预测下一条提示词、完成后展示简短 recap 三个方向。本文档 PR 不实现功能，也不表示相关能力已经可用。

研究日期：2026-10-24。DSH 源码基线固定为 [deepseek-harness@22ddee3](https://github.com/deepseek-ai/deepseek-harness/tree/22ddee3792402c3e70ec5f86a63c3e3e895a2f60)（2026-10-23）；目标仓库基线为 `zesming/dsh-plugins@892ce6e`。开发开始时需要重新核对上游变化。

## 方案定位

文中“已核实”表示固定基线源码或官方文档能够支持；“建议”表示本方案推荐的产品或技术选择；“待验证”表示开发前仍需实验或补充接口。产品参考能够证明交互方式，不能证明它们的内部提示词、模型路由或成本策略适合 DSH。

| 功能 | 建议归属 | 主要原因与实施前置 |
|---|---|---|
| 项目草稿 | DSH 现有导航与输入实现的修正 | 已有语义草稿和 workspace blank Session 复用；不增加第二份 `projectDrafts`。File / 图片的运行时归属必须单独验证 |
| 提示词预测 | 优先在 deepseek-harness 内验证第一方可选插件；宿主提供通用 suggestion 接口 | 已有安全插入动作，但尚未核实公开的 ghost text / 键盘接受接口；外部插件不能依靠内部 Lexical 实现交付完整体验 |
| 轮次 recap | 独立可选插件，Host 生成，Client 展示 | 已有 `turn/end` 与 `conversation.chat.turnTail`；语义摘要仍需辅助请求日志支持，不能声称外部插件零改动可运行 |

这里区分功能的合理归属，不在本次 PR 修改上游或创建上游 PR。未来在本仓库实现插件时，遵循 [CONTRIBUTING.md](../../../CONTRIBUTING.md)：不替换已发布组件，不抢占其他包的单占位 slot，使用宿主 UI primitives、可释放的注册和双语文案。

## 共用约束

- 项目、Session 和轮次不能混用：草稿属于现有 Session；workspace 决定导航；预测和 recap 必须绑定生成它们的历史版本。
- 两类辅助推理都可关闭、可取消、有超时及预算上限，不调用工具、不唤醒主 agent，不使用 `followup` / `inject` 伪装用户输入。可抽取轻量共享模块处理生命周期、取消、预算和并发；内容、UI 与缓存键独立，不为了少一次请求而强行绑定预测和 recap。
- 默认只处理已经发送的当前会话内容，不额外检索 memory、apps 或其他项目，也不默认上传未发送草稿。
- 凡进入模型请求的内容都必须遵守 DSH 的可追溯日志规则。`ctx.llm.prepareCall` / `stream` 只是推理原语，不能替代日志设计；外部插件不能使用受限的 `appendPluginRecord` 绕过它。
- 灰色是视觉层级，不代表低对比度：支持深浅主题、缩放、键盘和读屏；预测不能进入实际编辑文档，recap 不能混入主 agent 正文或后续模型历史。

## 建议开发顺序

1. 先统一项目导航并验证真实附件生命周期；该项不依赖模型服务。
2. 再打通通用 composer suggestion 接口，完成 Tab / → 的最终交互，再接预测生成、取消及预算控制。点击接受可以作为辅助入口，不能替代键盘需求。
3. 使用现有轮次终态与消息尾部接口实现 recap 的 `facts` 模式，再验证 `semantic` 的日志、预算和证据关联；两种模式分别声明能力，不让语义模式的接口缺口阻塞事实模式设计。

评审时优先确认三个问题：项目草稿的附件保留范围；预测对 Tab 焦点导航的仲裁；recap 在手动 stop / error 后如何呈现。其余实现前置与未验证项保留在对应文档中。
